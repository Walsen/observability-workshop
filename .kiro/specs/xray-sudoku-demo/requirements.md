# Requirements Document

## Introduction

The X-Ray Sudoku Demo is an end-to-end AWS reference application that showcases AWS X-Ray distributed tracing across a full request path: a browser-based Sudoku game, an API Gateway REST API, Python Lambda functions, and a DynamoDB table. The purpose of the demo is to produce a single, coherent X-Ray trace that begins in the frontend and flows through every backend component, including custom subsegments inside the Sudoku solver.

The frontend is a no-build static site (HTML/CSS/JS) hosted on AWS Amplify Hosting, connected manually through the Amplify console with Git branch-based live previews. The backend is defined as infrastructure-as-code using AWS CDK in Python and deployed separately. The two halves are joined by a manual handoff: the CDK deployment emits the API endpoint URL, which the operator configures in Amplify.

The game is fully playable and supports multiple concurrent users through a client-generated player identifier, with no managed authentication service.

## Glossary

- **X_Ray_Sudoku_Demo**: The complete demonstration application comprising the frontend, API, Lambda functions, and data store.
- **Frontend**: The static HTML/CSS/JS Sudoku game hosted on AWS Amplify Hosting from the `frontend/` folder in the repository.
- **Amplify_Hosting**: AWS Amplify Hosting, connected manually via the Amplify console using Git branch-based deployments and preview URLs.
- **API**: The Amazon API Gateway REST API that exposes the game endpoints.
- **Lambda_Function**: An AWS Lambda function written in Python 3.12 that handles a game endpoint and is instrumented with the AWS X-Ray SDK.
- **Solver**: The server-side Sudoku solving component that generates puzzles and solves boards using a backtracking algorithm.
- **Games_Table**: The Amazon DynamoDB table that stores game state, keyed by `gameId` and `playerId`.
- **Player**: A user of the game, identified by a client-generated `playerId`.
- **Player_Id**: A unique identifier generated by the Frontend to distinguish one Player from another without managed authentication.
- **Game_Id**: A unique identifier for a single Sudoku game instance.
- **Trace**: An AWS X-Ray trace representing a single end-to-end request path.
- **Trace_Header**: The `X-Amzn-Trace-Id` HTTP header used to propagate X-Ray trace context.
- **Subsegment**: A custom AWS X-Ray subsegment recorded within a Lambda_Function to capture a discrete unit of work.
- **CDK_App**: The AWS CDK application, written in Python, that defines the backend infrastructure (API Gateway, Lambda functions, DynamoDB table).
- **API_Endpoint_URL**: The invoke URL of the API, emitted as a CDK stack output after deployment.
- **Move**: A single value placement by a Player into one cell of the Sudoku board.
- **Canary**: An AWS CloudWatch Synthetics browser canary that, on a schedule, drives the deployed Frontend with a headless browser to exercise the New Game and Solve flows as a synthetic Player.
- **Canary_Target_URL**: The live Frontend URL (the Amplify_Hosting domain) that the Canary loads, supplied by the operator as a CDK context value (`canary_target_url`).
- **Alarm**: An Amazon CloudWatch alarm that transitions to the `ALARM` state when the Canary's success rate falls below a configured threshold.
- **Success_Percent**: The CloudWatch Synthetics `SuccessPercent` metric, the percentage of Canary runs that completed successfully over a period.

## Requirements

### Requirement 1: Client-originated end-to-end tracing

**User Story:** As a workshop attendee, I want a single X-Ray trace to span the browser, API, Lambda, and DynamoDB, so that I can see the complete request path in one trace.

#### Acceptance Criteria

1. WHEN the Frontend sends a request to the API, THE Frontend SHALL include a Trace_Header on the outbound request.
2. WHEN the API receives a request that includes a Trace_Header, THE API SHALL propagate the trace context to the invoked Lambda_Function.
3. WHEN a Lambda_Function calls the Games_Table, THE Lambda_Function SHALL record the DynamoDB call as part of the active Trace.
4. WHEN a request completes end to end, THE X_Ray_Sudoku_Demo SHALL represent the Frontend, API, Lambda_Function, and Games_Table calls within a single Trace.

### Requirement 2: Start a new game

**User Story:** As a Player, I want to start a new Sudoku game, so that I can begin solving a puzzle.

#### Acceptance Criteria

1. WHEN the API receives a newGame request that includes a Player_Id, THE API SHALL invoke the newGame Lambda_Function.
2. WHEN the newGame Lambda_Function is invoked, THE Solver SHALL generate a Sudoku puzzle with a unique solution.
3. WHEN the newGame Lambda_Function generates a puzzle, THE Lambda_Function SHALL assign a unique Game_Id to the puzzle.
4. WHEN the newGame Lambda_Function creates a game, THE Lambda_Function SHALL store the game state in the Games_Table keyed by Game_Id and Player_Id.
5. WHEN the newGame Lambda_Function completes successfully, THE Lambda_Function SHALL return the Game_Id and the initial board to the Player.

### Requirement 3: Retrieve an existing game

**User Story:** As a Player, I want to retrieve a game I previously started, so that I can resume playing.

#### Acceptance Criteria

1. WHEN the API receives a getGame request that includes a Game_Id and a Player_Id, THE API SHALL invoke the getGame Lambda_Function.
2. WHEN the getGame Lambda_Function is invoked with a Game_Id and Player_Id that exist in the Games_Table, THE Lambda_Function SHALL return the stored board state.
3. IF the getGame Lambda_Function is invoked with a Game_Id and Player_Id that do not exist in the Games_Table, THEN THE Lambda_Function SHALL return a not-found error response.

### Requirement 4: Submit a move

**User Story:** As a Player, I want to submit a move, so that I can fill in the board and progress toward a solution.

#### Acceptance Criteria

1. WHEN the API receives a submitMove request that includes a Game_Id, a Player_Id, and a Move, THE API SHALL invoke the submitMove Lambda_Function.
2. WHEN the submitMove Lambda_Function receives a Move, THE Solver SHALL validate the Move against Sudoku placement rules.
3. IF a submitted Move violates a Sudoku placement rule, THEN THE submitMove Lambda_Function SHALL return a response indicating the Move is invalid.
4. WHEN a submitted Move is valid, THE submitMove Lambda_Function SHALL update the stored board state in the Games_Table.
5. WHEN a submitted Move completes the board correctly, THE submitMove Lambda_Function SHALL return a response indicating the game is solved.

### Requirement 5: Solve the puzzle

**User Story:** As a Player, I want the server to solve the current puzzle, so that I can see the full solution.

#### Acceptance Criteria

1. WHEN the API receives a solve request that includes a Game_Id and a Player_Id, THE API SHALL invoke the solve Lambda_Function.
2. WHEN the solve Lambda_Function is invoked, THE Solver SHALL compute a complete solution for the current board using a backtracking algorithm.
3. WHEN the solve Lambda_Function computes a solution, THE Lambda_Function SHALL return the completed board to the Player.
4. IF the current board has no valid solution, THEN THE solve Lambda_Function SHALL return a response indicating that no solution exists.

### Requirement 6: Custom solver subsegments

**User Story:** As a workshop attendee, I want the solver's internal steps to appear as distinct X-Ray subsegments, so that I can inspect where time is spent inside the Lambda.

#### Acceptance Criteria

1. WHEN the Solver validates a board or Move, THE Lambda_Function SHALL record a Subsegment named `validate`.
2. WHEN the Solver generates a puzzle, THE Lambda_Function SHALL record a Subsegment named `generate`.
3. WHEN the Solver runs the backtracking algorithm, THE Lambda_Function SHALL record a Subsegment named `solve-backtracking`.
4. WHEN the Solver checks a completed board, THE Lambda_Function SHALL record a Subsegment named `check-solution`.

### Requirement 7: Multi-user support without managed authentication

**User Story:** As a Player, I want my games to be separate from other players' games, so that multiple people can use the demo at the same time.

#### Acceptance Criteria

1. WHEN a Player first uses the Frontend, THE Frontend SHALL generate a Player_Id.
2. WHILE a Player is using the Frontend, THE Frontend SHALL include the Player_Id on each request to the API.
3. WHEN a Lambda_Function reads or writes game state, THE Lambda_Function SHALL scope the operation to the Games_Table item identified by the Game_Id and Player_Id.

### Requirement 8: API Gateway tracing and CORS

**User Story:** As a workshop attendee, I want the API configured for tracing and cross-origin access, so that the Amplify-hosted frontend can call it and traces are captured at the API layer.

#### Acceptance Criteria

1. THE API SHALL have AWS X-Ray active tracing enabled.
2. WHEN the API receives a request from the Amplify_Hosting domain, THE API SHALL return CORS headers that authorize the Amplify_Hosting origin.
3. WHEN the API receives a CORS preflight request, THE API SHALL respond with the allowed methods and headers for the game endpoints.

### Requirement 9: Backend infrastructure as code

**User Story:** As an operator, I want the backend defined in CDK, so that I can deploy the API, Lambdas, and table reproducibly.

#### Acceptance Criteria

1. THE CDK_App SHALL define the API, the Lambda_Function set (newGame, getGame, submitMove, solve), and the Games_Table.
2. THE CDK_App SHALL configure each Lambda_Function to run on the Python 3.12 runtime with AWS X-Ray tracing enabled.
3. WHEN the CDK_App is deployed, THE CDK_App SHALL emit the API_Endpoint_URL as a stack output.
4. THE CDK_App SHALL target AWS region us-east-1.
5. THE CDK_App SHALL grant each Lambda_Function permission to write trace data to AWS X-Ray and to access the Games_Table.

### Requirement 10: Frontend hosting and deployment handoff

**User Story:** As an operator, I want the frontend hosted on Amplify and pointed at the deployed API, so that the demo is publicly reachable and connected end to end.

#### Acceptance Criteria

1. THE Frontend SHALL be a static site composed of HTML, CSS, and JavaScript that requires no build compilation step.
2. THE Frontend SHALL reside in a `frontend/` folder within the repository.
3. THE Frontend SHALL include an `amplify.yml` configuration that publishes the static files.
4. WHERE the operator provides the API_Endpoint_URL as an Amplify configuration value, THE Frontend SHALL send API requests to that configured URL.
5. WHEN the operator pushes the `main` Git branch, THE Amplify_Hosting SHALL deploy the Frontend to the production URL.
6. WHEN the operator pushes a `feature/*` Git branch, THE Amplify_Hosting SHALL deploy the Frontend to a preview URL.

### Requirement 11: Synthetic canary monitoring and alerting

**User Story:** As an operator, I want a synthetic browser canary that continuously exercises the deployed game and alarms on failure, so that a broken New Game or Solve flow surfaces automatically and each scheduled run produces an end-to-end X-Ray trace.

#### Acceptance Criteria

1. WHERE the operator provides the Canary_Target_URL as the `canary_target_url` CDK context value, THE CDK_App SHALL create the Canary; and WHERE the `canary_target_url` context value is absent, THE CDK_App SHALL synthesize the stack without the Canary.
2. WHILE the Canary is deployed, THE Canary SHALL run on a schedule of once every 5 minutes.
3. WHEN the Canary runs, THE Canary SHALL load the Canary_Target_URL in a headless browser, activate the New Game action, and assert that a 9×9 board renders.
4. WHEN the Canary has a rendered board, THE Canary SHALL activate the Solve action and assert that the board reaches the solved state.
5. WHEN the Canary runs, THE Canary SHALL have AWS X-Ray active tracing enabled so that the run produces a Trace spanning the Frontend, API, Lambda_Function, and Games_Table.
6. WHEN the Canary runs, THE Canary SHALL write run artifacts, including step screenshots, to a CloudWatch Synthetics artifacts store.
7. IF the Canary Success_Percent falls below the configured threshold over the configured number of evaluation periods, THEN THE Alarm SHALL transition to the `ALARM` state.
8. THE CDK_App SHALL grant the Canary only the permissions required to run the browser script, write artifacts, publish metrics, and write trace data to AWS X-Ray.
