# Development environment

Every project in this workspace gets a reproducible, declarative development
environment before any feature work starts. Two contributors on different
machines, and CI on a clean runner, must resolve the same toolchain from files
committed to the repository — never from whatever happens to be installed on
the host.

## Toolchain

| Tool | Owns | Where it is declared |
|------|------|----------------------|
| **devbox** | The whole non-Python toolchain, pinned per project | host prerequisite; manages `devbox.json` |
| **direnv** | Activating that toolchain on `cd`, deactivating on exit | host prerequisite; reads `.envrc` |
| **uv** | Python dependency resolution, locking, and the project virtual environment | `devbox.json` package; owns `pyproject.toml` + `uv.lock` |
| **python** | The interpreter version | `devbox.json` package |
| **just** | The documented command surface — test, lint, typecheck, synth, deploy | `devbox.json` package; recipes in `Justfile` |
| **jq** | JSON inspection in recipes and scripts | `devbox.json` package |
| **yq** | YAML inspection in recipes and scripts | `devbox.json` package |
| **aws-cdk-cli** | `cdk synth` and `cdk deploy`; the CLI is Node-based whatever language the constructs are written in | `devbox.json` package |
| **awscli2** | Ad hoc AWS inspection and deploy-adjacent commands, including `aws xray` trace inspection | `devbox.json` package |
| **git** | Version control, and the hook behavior CI depends on | `devbox.json` package |
| **gh** | Pull requests, releases, CI runs from the terminal | `devbox.json` package |

### Host prerequisites versus project packages

**devbox and direnv are host prerequisites, not project packages.** Devbox
cannot install itself, and direnv has to be on the shell *before* you enter the
directory or there is nothing to trigger activation. Install direnv once with
`devbox global add direnv` so it is available across every project, and hook it
into your shell. Everything else in the table above belongs in the project's own
`devbox.json` so it is versioned with the code that needs it.

**git is a project package even though the host already has one.** You need some
git to clone the repository, but only the pinned one is on the PATH inside the
environment, so hooks, config resolution, and subcommand availability behave the
same for every contributor and on a clean CI runner. That is a different case
from devbox and direnv, neither of which can be supplied by the environment they
are responsible for creating.

## Required files at the repository root

- **`devbox.json`** — the package list. Created with `devbox init`, populated
  with `devbox add <pkg>@<version>`.
- **`devbox.lock`** — committed. This is what makes the environment
  reproducible; without it the resolved versions can drift.
- **`.envrc`** — generated by `devbox generate direnv`, containing
  `eval "$(devbox generate direnv --print-envrc)"`. Committed, then trusted
  locally with `direnv allow`.
- **`Justfile`** — every command a contributor or CI stage needs to run.
- **`pyproject.toml`** + **`uv.lock`** — the backend's Python manifest and lock,
  owned by uv (see below). Both committed.
- **`.gitignore`** — must exclude `.devbox/`, `.venv/`, and any generated
  credential tree.

## Pinning

**Pin every devbox package to an exact version.** Devbox defaults an omitted
version to `@latest`, which pins nothing and lets the toolchain drift between
machines and between commits. This is the same rule the engineering practices
apply to application dependencies, extended to the tools that build them:

```json
{
  "packages": [
    "python@<exact>",
    "uv@<exact>",
    "just@<exact>",
    "jq@<exact>",
    "yq-go@<exact>",
    "aws-cdk-cli@<exact>",
    "awscli2@<exact>",
    "git@<exact>",
    "gh@<exact>"
  ]
}
```

Resolve each `<exact>` with `devbox search <pkg>` and commit `devbox.lock`
alongside. Upgrade deliberately, as its own reviewable commit, never as a side
effect of someone else's checkout.

Two package names need naming deliberately rather than by guess, because the
obvious spelling resolves to the wrong thing:

- `yq` is the Python wrapper around jq; **`yq-go`** is the Go implementation most
  recipes assume.
- **`aws-cdk-cli`** is the maintained CDK toolkit package. `nodePackages.aws-cdk`
  also exists and lags well behind; pinning it gets you a stale toolkit. Pinning
  `aws-cdk-cli` brings Node in as part of its closure, so there is no need to
  declare `nodejs` separately.

## Python: devbox provides the interpreter, uv owns the dependencies

Do not install Python packages with the interpreter devbox provides. A
Nix-installed interpreter cannot write to its own store path, and installing
globally would defeat the per-project isolation devbox exists to give.

- `devbox.json` pins the **interpreter version**.
- `uv` creates and manages the project virtual environment, resolves
  dependencies, and writes `uv.lock`.
- The backend keeps its own `pyproject.toml`.
- `uv.lock` is committed. It is what satisfies the exact-version requirement the
  specs place on direct dependencies.

**The dividing line is import versus invoke.** Anything application code
`import`s is a uv dependency. Anything a recipe or a shell invokes is a devbox
package. So `pytest`, `hypothesis`, `ruff`, `mypy`, `boto3`, `aws-xray-sdk`,
`aws-cdk-lib`, and `constructs` all live in `pyproject.toml` — none of them
belongs in `devbox.json`.

Two pairs in this stack are easy to file wrongly:

- **`aws-cdk-lib` is a uv dependency; `aws-cdk-cli` is a devbox package.** The
  constructs are Python and get imported. The `cdk` command is a separate
  Node-based binary and gets invoked. Both are needed, in different files.
- **`boto3` is a uv dependency; `awscli2` is a devbox package.** Same service,
  different layer: one is imported by the Lambda code, the other is a CLI for ad
  hoc inspection.

**`aws-xray-sdk` is a uv dependency.** It is imported by the Lambda code to
instrument handlers and to patch boto3. X-Ray *trace inspection* is done through
`awscli2` (`aws xray get-trace-summaries`, `aws xray batch-get-traces`); there is
no separate X-Ray CLI to pin.

## just is the command surface

Every command named in a spec or a README is a `just` recipe, so there is one
documented way to run each thing and CI and a contributor invoke the same code
path. At minimum: `just test`, `just lint`, `just typecheck`, `just synth`, and
`just deploy`.

A spec that requires "the single documented test command" is satisfied by a
recipe, not by a shell snippet pasted into a README.

## Frontend note

The frontend is a no-build static site — plain HTML, CSS, and JavaScript served
as-is by Amplify Hosting. There is no bundler, transpiler, or build step, so
there is no frontend toolchain to pin. Nothing about the frontend goes in
`devbox.json` or `pyproject.toml`; its only build-time artifact is a minimal
`amplify.yml` that publishes the static files.

## Optional tools

Add these per project when they earn their place; none is required by a spec.

- **`pre-commit`** — complementary to a pipeline check, never a substitute for
  one. A hook that can be skipped locally is not an enforcement boundary.

## A note on local networked dependencies

This project has no local container-runtime stack — there is no broker,
database, or other networked dependency to stand up on a developer's machine, so
no container client or Compose is pinned. If a future feature needs a local
networked dependency, add the container **client** (`docker-client`) and
`docker-compose` as pinned devbox packages, invoked through a variable so
`podman` can substitute; the container **engine/daemon** stays a host
prerequisite, since it cannot be supplied by a package inside the environment it
is meant to run.

## Constraints this must not break

- **Offline test guarantee.** Having `awscli2`, `aws-cdk-cli`, and `gh` on the
  PATH must not make any test depend on cloud access. Suites required to pass
  with no credentials and no network beyond localhost must keep doing so with the
  full toolchain present — which for the CDK means synthesis must resolve nothing
  from an account, since template synthesis and the assertions over its output
  are part of that offline suite.
- **No secrets in committed files.** Environment variables that carry secrets
  are supplied at runtime. `.envrc` may export non-sensitive configuration and
  must never contain a key, token, or credential path holding real material.
  Use a git-ignored `.env.local` or the platform secret store instead.

## Bootstrapping a new project

1. `devbox init`, then `devbox add` each tool at an exact version.
2. `devbox generate direnv` and `direnv allow`.
3. `uv init` for the backend, then `uv add` its dependencies; commit `uv.lock`.
4. Write the `Justfile` recipes the specs and README refer to.
5. Add `.devbox/`, `.venv/`, and any generated credential tree to `.gitignore`.
6. Commit `devbox.json`, `devbox.lock`, `.envrc`, `Justfile`, `pyproject.toml`,
   and `uv.lock` together, so the environment is reproducible from that commit
   on.
